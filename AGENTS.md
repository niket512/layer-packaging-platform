# Architecture rules
- Packaging browsing uses local box and pouch reference catalogues with family-specific combined filters, same-page details and a device-local shared shortlist; selected IDs, names and supported attributes prefill the existing chat, with a composite reference photo using its existing attachment path, to preserve multi-design requests without new submission schemas or invented buyer/manufacturer specifications.

- Procurement (RFQs, quotes, POs, suppliers) lives at `/dashboard/procure` with real Cloud auth and `user_roles` (founder/supplier); the catalogue dashboard keeps its no-login brand link — suppliers must only ever see their own data.
- Suppliers are linked to founders by the email on the founder's `suppliers` row matching the supplier's sign-in email — avoids a separate invite-token system.
- AI helpers go through the `procure-ai` edge function (Lovable AI, `openai/gpt-6-astra`) — keeps keys server-side.
- The manufacturer marketplace (search, store, admin review) is served on the `app.` subdomain (and `/app/*` elsewhere) by hostname check in `App.tsx` — one Lovable project, one deployment.
- Admin rights come only from an `admin` row in `user_roles` checked via `is_admin()`; users can never self-assign it.
- Catalogue PDFs go to the private `catalogue-pdfs` bucket; the browser sends the PDF's page text (or, for scanned PDFs, small page pictures) to `extract-catalogue` in small batches with a non-streamed AI call, because whole large PDFs exceed the edge function's CPU limit. Products come back as drafts with page + photo box; photos are cropped in the browser and stored as small JPEG data URLs on the row because public storage buckets are blocked for this workspace.
- Directory profiles in `src/data/manufacturers.ts` carry a `categories` array (bottles/sachets/boxes) rather than one category, so a maker that supplies several product families appears under each heading without duplicating the record.
- The public Manufacturer Discovery page (`/manufacturers`, `/manufacturers/:slug`) reads from `src/data/directory.ts` through an async fetcher with a `listing_status` gate — so it can be swapped for a backend table later without UI changes, and unconfirmed facts stay null instead of guessed.
- The public sourcing workspace at `/sourcing` uses the isolated `intake` mode of `directory-search` without manufacturer data or recommendations; conversations stay device-local and phone-confirmed requests go to `requirement_submissions` for private human follow-up, leaving ordinary directory search unchanged.
- Sourcing requests opt into conversational clarification in `directory-search`; persist question topics with turns and enforce the question budget client-side so ordinary directory search remains unchanged and earlier questions are not repeated.
- Sourcing intake topic validation and category-specific question configuration share a pure TypeScript module in `supabase/functions/_shared/sourcing-intake.ts` — keeps the client allowlist aligned with the intake prompt without changing directory matching.
- Sourcing intake analyzes each non-contact message through streamed structured conversational replies with explicit intent/stage state; quotationAsked blocks a second quotation round while completed replies and attachments remain saved — avoids advancing on greetings, refusals or unrelated replies.
- Initial sourcing images are validated server-side and sent as typed Responses image parts alongside the request; design completion derives from sent chat attachments or a chat reply — enables image-aware quotation questions without a separate upload step.
- Sourcing follow-up prompts are recorded on conversation turns and rendered from that saved history rather than current-step conditions — preserves chronological design and contact questions after replies and submission.
- Sourcing briefs are extracted in the existing intake response with allowlisted topics and evidence sources; buyer edits are saved locally and sent with subsequent context and the existing submission text — avoids extra AI calls or a mandatory review step while preserving corrections and unknowns.
